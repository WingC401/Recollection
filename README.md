## 実装モジュール

### BlockDissolve.shader / TeleportEffectController.cs — テレポートディゾルブ

#### 制作動機

最初のテレポート演出は、プレイヤーの周囲に複数のリングを展開し、回転しながら包み込んで瞬間移動するというものでした。
しかし、チームメンバーや試遊した友人・指導教員から「魔法のように見えて SF の世界観から外れている」という指摘を受けました。
そこでリファレンスを集め直し、「データのパケット転送」をモチーフに、プレイヤーのメッシュをブロック単位で分解・転送する表現へ変えることをチームで決めました。
パーティクルでは狙った見た目にならなかったため、ネットでリファレンスを探し、メッシュの頂点を直接操作する方式にしました。チーム制作で初めて、HLSL のカスタムシェーダーによるエフェクトに挑戦しています。

#### 工夫した点

- ブロックの大きさと消える順番の両方にばらつきを持たせるため、グリッドを 2 段にしています。まず 1m 単位の粗いグリッド（`floor(worldPos)`）でそのセルのブロックサイズを決め（`lerp(BlockMinSize, BlockMaxSize, rand)`）、次にそのサイズのグリッド（`floor(worldPos / blockSize)`）で消える順番の乱数を決めています。`DissolveProgress` がその乱数を超えた瞬間から、ブロックが Y 方向へ飛び上がります
- ブロックが上へ流れていく「データが飛んでいく」見た目は、頂点シェーダーで「`DissolveProgress` がそのブロックの乱数を超えたら上へ飛び始める」オフセットを加えることで作っています
- `DissolveProgress` は外部（`TeleportEffectController.cs`）から制御できるようにしています
- `EaseIn` / `EaseOut` 関数で、ブロックが上へ飛ぶスピードに緩急をつけています
- `StartDissolve()` と `ReverseDissolve()` でテレポートの開始と戻りを分けて制御しているため、プレイヤーの入力管理（`InputPermission`）を切り替えるタイミングも簡単に管理できます
- 演出が重複しないよう、既存のコルーチンを `StopCoroutine` で止めてから再起動するようにしています

#### 苦労した点

- ワールド座標に直接ノイズをかける実装を試しましたが、砂状の細かい消え方になり、テレポートというよりキャラクターが「消滅した」ように見えてしまいました → `floor()` でグリッドに揃えて、ブロック状の消え方にしました
- ブロックサイズが均一で、見た目が単調すぎました → 2 段のグリッドでブロックのサイズをランダムにしました
- Y 方向の飛び上がりオフセットを追加したとき、ブロック 1 個ずつではなくキャラクター全体が引き延ばされるバグが出ました → `noise` と `DissolveProgress` の比較で、飛ぶタイミングをブロックごとに別々にしました
- `ReverseDissolve` 完了後に `originalMaterial` の復元が漏れ、キャラクター全体が真っ白になりました → 元のマテリアルを `Awake()` で保存し、`DissolveAndRestore` コルーチンの最後で必ず `ApplyMaterial(originalMaterial)` を呼んで戻しています
- 分身（エコー）がテレポート切替ボタンを作動させて本来の行き先が無効になり、テレポート中に参照している行き先が消えてプレイヤーの挙動がおかしくなるバグがありました → テレポートが発動した瞬間に行き先の位置を変数に保存し、テレポート完了まで入力を受け付けないようにして解決しました

#### 注目ポイント

頂点シェーダー内でワールド座標をグリッド分割し、ブロックごとに独立したランダムノイズ値を生成している部分（`vert` 関数内）です。
ノイズ値に基づいてブロックが上方向に飛んでいくオフセット処理と、フラグメントシェーダー側の `discard` によるブロックの消滅タイミングも、同じ乱数で制御しています。

### ScreenDoor.shader — 障害物透過（ディザリング）

#### 制作動機

本作はパズルゲームなので、ギミックを解くにはフィールド全体を観察する必要があります。
そのため、カメラと障害物に衝突判定を設けてカメラを押し戻す手法ではなく、カメラに近いオブジェクトをシェーダー側で透過させ、視界を常に確保する方針を選びました。
カメラの挙動をシンプルに保ちつつ、パズルゲームとして最も重要なプレイヤーの視認性を確保するためです。

#### 工夫した点

- 半透明（アルファブレンド）ではなくディザ抜きを選んだ理由：半透明は描画順に依存するので、ブロックが重なる場面で前後が入れ替わって見えます。深度も書かないため、ステンシルで描くプレイヤーのシルエット表示と両立できません。そこで、Opaque のまま深度とステンシルを保ちつつ透過して見せられるディザリング（スクリーンドア透過）方式を採用しました
- `ShadowCaster` パスを別途実装し、影の描画が正常に機能するようにしました
- URP の PBR ライティング（`UniversalFragmentPBR`）の計算後にディザ抜き処理を追加することで、ライティングを維持しながら距離に応じて透過できるようにしました
- ライティングなしの軽量 Pass（Pass2）と PBR ライティングありの Pass（Pass3）の両方に、ディザ抜き処理を実装しました
- 障害物領域を `Stencil` バッファへの書き込み（`Ref=1`）でマークする設計により、Player・Echo・Goal のキャラクター側シェーダーのシルエット描画と連動できるようにしました

#### 苦労した点

- Pass2 と Pass3 のどちらか片方だけにディザを入れると、もう片方の不透明なピクセルが残りました → 原因は、Pass2 に `LightMode` を指定していないため URP が `SRPDefaultUnlit` として描画し、Pass3（`UniversalForward`）と両方が毎フレーム描かれていたことです。両パスにディザを入れて解決しました
- Bayer テクスチャの UV にオブジェクト UV を使うと、カメラ移動時にパターンが泳いで見えました → Pass2 では `ComputeScreenPos()` で取得したスクリーン座標（ピクセル座標 ÷ `_BlockSize`）に変更して解決しました。Pass3 は `SV_POSITION` から計算していますが、`w` で割っているため距離でパターンの密度が変わる式になっており、`SV_POSITION.xy / _BlockSize` に揃えるのが今後の改善点です

#### 注目ポイント

Pass2（ライティングなし）と Pass3（PBR ライティングあり）の両方に実装しているディザ抜き処理です。
Pass3 の `Stencil` バッファへの書き込み（`Ref 1` / `Comp Always` / `Pass Replace`）によって、Player・Echo・Goal のシェーダーのシルエット描画と連動しています。
本シェーダーは障害物の描画領域を `Stencil=1` でマークする役割のみを担い、シルエットの判定・描画はキャラクター側の各シェーダーが行う 2 段階の設計です。
キャラクター側は、マークされた障害物領域のうち自身が障害物に隠されている部分のステンシル値を `2` へ更新し、`Stencil=2` の領域にのみシルエットを描画しています。

### TeleportLine.shader — テレポート先を示す誘導ライン

#### 制作動機

テレポートの行き先をプレイヤーに直感的に示すために、テレポーターと目標地点の間に、流れる破線のアニメーションを表示しています。
静止した線では向きが伝わらず見えづらいため、UV をスクロールさせて流れる線にしました。

#### 実装のポイント

- テクスチャは使わず、`fmod(uv.x + time * MoveSpeed, Width)` で UV を周期ごとに区切り、`Distance` 以下の区間だけ描いて、それ以外は `clip` することで破線を作っています
- デザイナーが「どれを触れば何が変わるか」を説明なしで分かるように、動きに関わるパラメータは速度（`MoveSpeed`）・周期（`Width`）・線の割合（`Distance`）の 3 つに絞っています（あとは色だけです）
- `Stencil` に `Ref=1` を書き込み、ScreenDoor と同じくキャラクター側シェーダーのシルエット描画と連動しています

### StageStartCameraWork.cs — ステージ開始カメラワーク

#### 制作動機

ステージ開始時にゴールの位置をプレイヤーへ伝えるカメラ演出を実装しました。
また、制御点を Inspector で増減でき、Gizmos で軌跡を確認できるエディタとして作っています。
Hermite 曲線を採用した理由は主に 2 点あります。

1. ステージ全体を俯瞰する軌跡でゴールまでを見せることで、プレイヤーがフィールドを直感的に把握できるようにするため
2. 直線移動ではカメラがステージ内のブロックや壁をすり抜けてしまうため、曲線で障害物を回り込む経路にするため

#### 工夫した点

- `null` 参照が発生しないよう、制御点リストのクリーンアップ処理を `Start()` で実行しています
- `Time.unscaledDeltaTime` を使用し、TimeScale の影響を受けずに演出が再生されるようにしています
- カメラワーク完了後にプレイヤーの入力（`InputPermission`）を有効化し、プレイヤー操作の開始タイミングがずれないように制御しています
- `OnDrawGizmos()` によりエディタ上でパスを可視化しています。インスペクターから制御点を自由に増減・配置でき、プログラマー以外のメンバーでも演出を調整できるツールとして設計しました

#### 苦労した点

- Hermite 曲線の数式をコードに落とし込む際、接線ベクトル（`m1`, `m2`）の方向と強さの調整が難しく、意図した軌跡を描くまで試行錯誤しました
- カメラオフセットをプレイヤーの向きに合わせて回転させる処理で、クォータニオンの掛け算の順序に注意が必要でした

#### 注目ポイント

`GetHermitePathPosition()` 関数内の Hermite 曲線計算と、`OnDrawGizmos()` によるエディタ上でのパス可視化です。
インスペクターから制御点を自由に増減・配置でき、プログラマー以外のメンバーでも演出を調整できるツール設計にしています。

### TutorialUI.cs / TutorialRenderer.cs — マルチデバイス対応のチュートリアル UI

#### 制作動機

審査員やプレイヤーがキーボードとコントローラーのどちらで遊ぶか分からないため、どちらでも常に分かりやすい操作ガイドが出るようにしました。
デバイスを切り替えた瞬間に UI が更新されるので、プレイヤーが混乱せずにプレイを続けられます。

#### 実装のポイント

- `TutorialRenderer` がステージごとの表示内容（キーボード用テキスト・ゲームパッド用テキスト・ハイライトするボタン）を持ち、`TutorialUI.SetTutorialText()` に渡しています
- テキスト中の `[上ボタン]` `[WASDキー]` のようなキーワードを辞書（`tagToButtonIcon`）で引き、TextMeshPro のスプライトタグ `<sprite=N>` に自動置換しています。デザイナーはアイコン番号を知らなくても、日本語のキーワードを書くだけでボタン画像を出せます
- 置換はキーボード用・ゲームパッド用の 2 つのテキストに対して事前に行い、`Update()` で `Gamepad.current` の有無を毎フレーム確認して、表示するテキストとアイコンを入力デバイスが切り替わった瞬間に反映しています
- ハイライトするボタンの位置はコントローラー画像上の座標表（`ButtonPos`）で持ち、点滅はアルファを `cos` で振って表現しています
